## 待办 1 — `/compact` 报 11148 `tool_call_sequence_broken`

**现象**
```
Error during compaction: API Error: 400 upstream client (http 400):
{"code":11148,"msg":"tool calls and tool results do not match, please start a new conversation and retry",
 "extError":{"code":"tool_call_sequence_broken","message":"tool calls and tool results do not match, ..."}}
```

**证据（本地代码 + 实测数据）**
- `grep 11148` 全仓 **零命中**：`internal/upstream/classify.go` 只处理 11128 / 11102（模型通道）、
  11140（内容审核），11148 **未被识别**。
- 400 → `Classify()` 落到 `if status >= 400 { ... return ErrClient }`（classify.go:133-139），
  与 11128 同档处理。
- `handler.go` 的 `ErrClient + IsModelChannelRejected` 分支会**换账号重试**；而
  `IsModelChannelRejected` 靠 `e.Code`（11128/11102）或关键词判定，**11148 两条都不命中**
  （classify.go:192-209）→ 直接 400 甩给客户端。
- 本地 `data/usage.json`：最大单次 `total_tokens = 559,405`，>200k 的有 17 次，
  >100k 的 84 次（中位数 6 万）。说明**超长上下文是常态**，断链更容易暴露。

**结论（对用户推测的修正）**
用户推测「某次工具调用被打断 / 手动删了历史消息」——**部分正确但不完整**。真实机制分两层：

1. **上游是强校验**：要求每个 assistant 的 `tool_calls` 后紧跟配对的 `tool` 结果，ID 必须一一对应。
   `/compact` 会把**全量历史**发上去，任何一处不配对就整条拒绝。
2. **本网关会主动制造不配对**——这才是关键，且是"必然踩到"而非偶发：
   - `sse.go` 的 `IsEmptyToolResponse` 认为「空 tool_calls 响应」不可用 → 触发**换号重试**；
   - 但**出错的那一轮 assistant 消息（含 tool_calls）已经被流式写进客户端历史**，
     重试得到的第二条 assistant 消息（可能没有 tool_calls）也已写入；
   - `sse.go:307-316` 的 `renameToolCallID` 把 `tool_call.id` 改写成 `toolu_` 前缀，
     于是**重试前后生成的 tool_call id 不同**，配对的 tool 结果只能对上其中一个；
   - 历史里就留下了「孤儿 tool_call」或「孤儿 tool result」→ 11148。
3. **次因**：CC Switch 模式下 Claude Code 以为上下文还有余量，很少主动压缩；一旦 `/compact`
   把 559k tokens 全量上送，历史里早先累积的断点集中爆发。

**处置（上游已明确给出）**
- 立刻可用：`/clear` 或 `claude -c` 之外新建会话——上游原话
  *"please start a new conversation and retry"*。
- 折中：`claude --resume <id> --fork-session` 从历史分叉，再让它尽早压缩。
- **不建议**手工编辑 `~/.claude/projects/**/*.jsonl` 删消息——配对是链式的，删一条会造出新的断点。

**代码侧待办（三选一或组合）**
- [ ] `modelChannelBlockedCodes` 加 `11148`，或新增 `IsBrokenToolSequence(e)` 判定，
      命中时**换账号重试**而不是 400（换号能拿到一份干净的上下文？——需实测确认，因为
      断链在请求体里，换号大概率一样 400，**所以这条要先验证再动手**）。
- [ ] 更可能有效的方向：`IsEmptyToolResponse` 换号重试时，**保证重试轮不把两条 assistant
      消息都写进历史**；或重试时沿用同一条 `tool_call.id`（不在重试轮二次 `renameToolCallID`）。
- [ ] 给 11148 一个专门的 `ErrKind`（如 `ErrBrokenToolSeq`），映射成**明确文案**，
      提示"请新建会话"，而不是把裸 400 透给客户端——至少让用户看得懂。

## 待办 2 — Claude Code 没有上下文进度条

**现象**：Claude CLI 底部不显示 context 占用（如 `12% used`）。

**证据（本机 `~/.claude/settings.json`）**
```json
"ANTHROPIC_BASE_URL": "http://127.0.0.1:15721",          ← 指向 CC Switch，不是网关
"CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT": "1",
"ANTHROPIC_DEFAULT_OPUS_MODEL": "claude-opus-5[1M]",
"ANTHROPIC_DEFAULT_OPUS_MODEL_NAME": "deepseek-v4.1-flash",
"CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1"
```
而 `claude-profiles/wb-local.example.json` 里映射的是 `deepseek-v4.1-flash[1M]`。

**结论**
上下文进度条 = **已用 token ÷ 模型窗口**。本网关的模型表虽然会回 `context_length`，
但上游模型名 `deepseek-v4.1-flash` **不在 Claude Code 内置的窗口表里**，于是分母取不到；
再叠加 `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1`（该开关的本意就是
"未知模型不做窗口限制/不报错"），**分母缺失 → 进度条无处渲染**。

注意这是**客户端侧的显示问题，与网关能否服务无关**——所以两边表现不一致：
- 走本机 profile（`..._MODEL_NAME` = `deepseek-v4.1-flash`）→ 无进度条；
- 走 CC Switch（`..._OPUS_MODEL` = `claude-opus-5[1M]`，带 `[1M]` 后缀）→ 有进度条。

**待办**
- [ ] 在 profile 的 `ANTHROPIC_MODEL` 上加窗口后缀（如 `deepseek-v4.1-flash[1M]`）试试是否恢复；
      `[1M]` 是 Claude Code 的窗口标注语法，`claude-profiles/*.example.json` 里
      `ANTHROPIC_DEFAULT_*_MODEL` 已经这么写了，但 `ANTHROPIC_MODEL` 本身没带。
- [ ] 若无效，改用 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` 让它按 `/v1/models` 的
      `context_length` 取值——需确认本网关 `/v1/models` 是否真的返回了 `context_length`
      （`listModels` 仅当 `m.ContextLen > 0` 才带该字段，而 `ContextLen` 取自上游
      `max_input_tokens` 等字段，**上游可能压根不给**）。
- [ ] 明确区分：这条**不是 bug**，是显示能力缺失；不要为它去改网关的协议层。

## 执行记录（2026-09-19 第二轮）

### ✅ 已完成 — 待办 1：11148 文案

按「先修文案、不动重试策略」的既定顺序实施（**换号重试那条仍待实测**）：

- `classify.go` 新增 `ErrBrokenToolSeq` 类别 + `brokenToolSeqCode = 11148` 常量 +
  `String()` 返回 `"broken_tool_sequence"`。
- `Classify()` 中**优先于 `hardMarkers`** 判定 11148——否则错误文案里的
  "do not match" 之类措辞可能被 `hardMarkers` 抢先判成 `ErrHardCredit` 而误冷却 12h。
  判据：`code == 11148` **或** body 含 `tool_call_sequence_broken`。
- `handler.go` 的 `forwardStream` switch 新增分支：**直接交回调用方**，
  不换号、不冷却、不 NoteError（断链在请求体里，这些动作全是误伤）。
- `statusForKind()` 映射为 **400**（而非 429/503）——避免诱导客户端「稍后重试」，
  因为重试永远不会成功。
- 新增 `hintBrokenToolSeq()`：给上游英文原文补一段中文可操作提示
  （`/clear` 新建会话 / `--fork-session` 分叉）。
- 回归测试：`TestClassify` 增加 2 个用例（完整 11148 报文 + 仅 marker），**已通过**。

验证：`go build ./...` / `go vet ./...` / `go test ./...` 全绿。

### ⚠️ 待办 2 的实际结论：补 `[1M]` **修不好进度条**

已把两处 `ANTHROPIC_MODEL` 补成 `deepseek-v4.1-flash[1M]`
（`wb-local.json`、`wb-nas.json`、两个 `.example.json`），但**实测发现根因不在这里**：

```
$ curl /v1/models
models: 19
any with context_length: 0      ← 一个都没有
any with cost_factor:    12
```

且返回的是**静态兜底表**（带 `cost_factor` 是特征），说明**上游压根没给窗口信息**：
`models.go:161` 从 `max_input_tokens` 等字段取 `ContextLen`，上游不返回 → 恒为 0 →
`listModels`（handler.go:282）仅当 `ContextLen > 0` 才输出 `context_length` → 字段整个消失。

**结论**：分母既不能从模型名推断（`deepseek-v4.1-flash` 不在 Claude Code 内置窗口表），
也不能从 `/v1/models` 拿到（上游不给），所以**进度条无从渲染**。
`[1M]` 后缀只是让 Claude Code 本地认为"窗口 1M"，是**缓解**而非修复。
真正的修复要么在上游侧（不可控），要么在网关侧**给兜底表补上合理的 context_length**。

- [ ] 决策：是否在 `FallbackModels()` 的静态表里补 `ContextLen`
      （如统一填 200k/128k，或按模型分别标注）。**这是有副作用的改动**——
      填错会让 Claude Code 在超限前不预警，反而不如现在"不显示"安全。

## 附：一条环境事实（与上面三问都相关）

本机 `~/.claude/settings.json` 的 `env` 段把 `ANTHROPIC_BASE_URL` 指向
`http://127.0.0.1:15721`（**CC Switch**），且优先级高于进程环境变量。
因此**不带 `--settings` 启动时，请求走的是 CC Switch 而非本网关**。
`docs/usage.md` 已就此写过警告；上面 11148 与进度条两个问题都因此出现"两边不一致"的表象。
